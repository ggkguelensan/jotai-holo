# Модель профиля: команда → факт → реакция

Пользователь меняет черновик и нажимает Save. Команда валидирует данные и сохраняет их через API. Только успешный ответ порождает факт `profileSaved`. Модуль уведомлений реагирует на этот факт, не управляя сохранением.

## Модель и async-политика

<<< @/../examples/documentation.tsx#workflow

Пока запрос выполняется, повторный save игнорируется. Входной draft снимается до await, поэтому дальнейшее редактирование не меняет отправленные данные. Ответ сохраняется в `$profile`; текущий draft не перезаписывается, так что новые правки не теряются. Ошибка попадает в `$error`, успех-событие не публикуется, `$saving` очищается в finally.

Это явно выбранная политика примера, а не встроенное поведение actionAtom. Для latest-wins, отмены и повторов нужна другая политика модели или готовый data-fetching инструмент.

## Независимая реакция

<<< @/../examples/documentation.tsx#bond

Факт уже произошёл; уведомление — последствие. Отключение уведомлений не отменяет успешное сохранение. Здесь нет события `nameChanged`, которое само изменяет имя: команда и факт имеют разные роли.

## Владение соединением

<<< @/../examples/documentation.tsx#runtime

Создайте runtime до рендера приложения. Передайте `runtime.store` в `<Provider store={runtime.store}>`, привяжите атомы `runtime.model` через holo вне render и вызовите `runtime.dispose()` при завершении сессии. На сервере создавайте runtime на каждый запрос, не на уровне общего модуля. Для scoped DI используйте отдельный Bunshi-адаптер.

Ошибка API — ожидаемое состояние модели; onError соединения предназначен для ошибок самой реакции. Этот пример обрабатывает API-ошибки внутри save и не пробрасывает их вызывающему View.

## Привязка редактора

<<< @/../examples/documentation.tsx#profile-view

Вызовите `const Editor = createProfileEditor(runtime.model)` один раз при создании приложения, затем отрисуйте `<Provider store={runtime.store}><Editor /></Provider>`. Фабрика создаёт определение компонента; её нельзя вызывать внутри render другого компонента. View не импортирует атомы и не обрабатывает ошибки сохранения самостоятельно.

## Проверка сценария

Исходник примера входит в TypeScript-проверку. Тесты `tests/documentation.test.ts` проверяют отсутствие факта до ответа API, один запрос при повторном save, доставку успешного факта, прекращение реакции после dispose, ошибку API и отклонение невалидного ввода.
